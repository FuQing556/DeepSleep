# 19｜双人联机与热更新架构规格 v1.0

> 最后更新：2026-09-04  
> 读者：第一次接触Unity联网和热更新的开发者  
> 状态：架构已确定；具体包版本需在Unity 6.6新工程建立后逐项验证锁定

## 1. 先理解两个概念

### 1.1 联机不是“同步两个Transform”

两台电脑会各自运行一份游戏。如果双方都能随意决定伤害、掉落和Boss状态，很快就会出现一边Boss已死、另一边仍在攻击的分歧。项目采用“主机权威”：房主设备同时承担服务器职责，客人设备把操作指令发给主机，主机决定关键结果并广播。

### 1.2 热更新分资源和代码

- **资源热更新**：不重新安装APK/EXE就下载图片、音频、关卡、配置和资源包。
- **代码热更新**：不重新安装就下载新的C#程序集，让玩法逻辑发生变化。

资源热更新先实现；代码热更新预留边界，等本地战斗与联网切片稳定后再接入。两者不能混成一个“下载更新”类。

## 2. 首发技术选择

| 领域 | 选择 | 原因 |
|---|---|---|
| 游戏对象联网 | Netcode for GameObjects | 两人、GameObject/MonoBehaviour式2D项目，认知成本相对可控 |
| 传输 | Unity Transport | 与Netcode for GameObjects直接配套 |
| 本机测试 | Loopback/Host模式 | 不需要公网即可验证命令和权威逻辑 |
| 局域网 | 直接地址连接适配器 | 排除大厅和中继后单独验证战斗同步 |
| 公网 | 可替换的房间与中继适配器 | 国内可达性需要实测，不能把玩法绑死在某家云服务 |
| 资源热更新 | YooAsset候选，迁移后做版本验证再锁定 | 支持单机、联机更新、缓存、校验和多平台资源交付 |
| C#代码热更新 | HybridCLR候选，后置接入 | 面向IL2CPP动态程序集；接入会改变构建链，不能抢跑 |

程序只能依赖项目自己的接口，例如 `ISessionService`、`ITransportAdapter`、`IContentUpdateService`；具体第三方包放在适配器程序集。更换服务时不允许修改玩家、Boss和关卡代码。

## 3. 联机拓扑

```text
房主设备
├─ 权威游戏模拟
├─ 房主本地玩家输入
├─ 未占用角色的同伴AI（如有）
└─ 网络服务器
        ⇅ 指令与快照
客人设备
├─ 客人本地输入
├─ 本地表现与预测
└─ 网络客户端
```

首版不做独立服务器。房主退出意味着房间结束；不实现主机迁移。客人断线时，主机立刻用AI接管客人角色，使战斗继续，并显示重连状态。

Windows 与 Android 运行同一套权威战斗逻辑、网络消息和稳定ID。消息不得传递平台特有的按键、像素坐标或本地资源路径，只传已经转换后的 `PlayerCommand` 和权威状态，因此电脑↔手机、电脑↔电脑、手机↔手机不需要三套联机实现。

## 4. 房间流程

### 4.1 双人游戏入口

```text
双人游戏
├─ 快速匹配
│  └─ 选择角色 → 按角色与兼容版本排队 → 匹配成功 → 准备房间
├─ 创建私人房间
│  └─ 生成房间码 → 房主选择/占用角色 → 等待另一设备加入
└─ 加入私人房间
   └─ 输入房间码 → 选择剩余角色 → 双方准备
```

快速匹配采用“先选角色、后匹配”。因为队伍只能有一蓝一黑，系统只把DeepSeek队列与Harness队列配对，从根源消除进房后抢角色。私人房间允许房主先选角色，加入者看到剩余槽位；准备前任一方可发起交换，双方确认后交换。

### 4.2 私人房间创建与加入

1. 玩家选择“在线合作”。
2. 房主创建私密房间。
3. 系统生成房间码或邀请信息。
4. 房主选择尚未占用的角色并准备。
5. 客人加入、完成版本检查、选择另一角色并准备。
6. 主机确认双方客户端版本、内容版本、协议版本和章节解锁条件兼容。
7. 双方加载同一章节；均报告准备完成后，主机开始倒计时。

这条流程就是电脑创建、手机输入房间码的测试入口。两台电脑或两台手机走完全相同的流程，不建立平台专用房间。

### 4.3 快速匹配

1. 玩家选择角色、可接受难度和可进入章节范围。
2. 匹配服务只寻找另一角色、协议兼容、内容兼容的玩家。
3. 匹配成功后服务建立临时房间并指定主机。
4. 若一方是Windows、一方是Android，首版主机选择策略优先考虑前台稳定性和网络质量；具体权重来自服务配置，不在客户端写死“电脑永远是主机”。
5. 双方进入准备房间，可查看对方平台和延迟，但不能改成重复角色。
6. 准备后加载并开始章节。

快速匹配依赖可部署的匹配服务，因此排在私人房间和公网中继稳定之后。它不改变底层战斗同步，只新增玩家配对入口。

### 4.4 准备房间

- 显示房主/客人、Windows/Android平台、延迟、角色槽位、章节、难度、客户端版本、内容版本和准备状态。
- 修改角色、章节或难度会清除双方准备状态。
- 私人房间允许交换角色；快速匹配不允许改成重复角色，可退出后以另一角色重新排队。
- 房主只能在双方版本通过且均准备时开始。
- 手机切到后台时立即显示“暂离”；超过配置时限视为断线。

### 4.5 加入失败必须说明原因

禁止只显示“连接失败”。至少区分：

- 房间不存在或已关闭。
- 房间已满。
- 角色槽位冲突。
- 游戏基础版本不兼容。
- 联机协议版本不兼容。
- 资源内容版本不兼容且更新失败。
- 中继/网络不可达。
- 加载超时。

### 4.6 断线

- 客人断线：主机标记该槽位为 `AI_Takeover`，由AI从下一模拟刻接管。
- 客人重连：完成版本和身份令牌校验后，主机在安全同步点把控制权交还。
- 房主断线或主动退出：当前章节结束，客人返回结果/房间中断界面；首版不迁移房主。
- 战斗中的网络抖动不能让角色突然失去碰撞、获得无限能量或重复结算技能。
- Android进入后台、锁屏或切换网络必须按潜在断线处理；手机作为房主时尤其可能结束整局，因此私人组队界面可以提示“电脑作为房主通常更稳定”，但不禁止手机开房。

## 5. 权威边界

### 5.1 主机唯一决定

- 敌人和Boss生成、阶段、生命和死亡。
- 玩家伤害、倒地、救援完成和复活。
- 玩家弹与敌弹的玩法命中结果。
- 掉落生成、归属和拾取结果。
- 技能能量消耗、冷却和Harness清弹结果。
- 强化候选、选择结果和章节推进。
- 随机种子和受约束随机事件。

### 5.2 客户端可以立即表现

- 自己角色的移动动画、后坐、按钮反馈和非玩法粒子。
- 瞄准圈和技能合法性预览；最终释放仍由主机确认。
- 本地预测的移动；收到主机快照后平滑校正。
- 不会影响伤害的命中特效预测；被主机否决时必须能安全回收。

### 5.3 禁止同步的东西

- 每一粒纯装饰粒子。
- Animator每个内部参数。
- 背景滚动每帧Transform。
- 可以由已同步事件在本地重建的声音、闪光和残影。

## 6. 网络数据模型

### 6.1 稳定标识

每个角色、技能、弹体、敌人、Boss Pattern、掉落和关卡配置都使用稳定ID。网络消息只传ID和必要状态，不传Prefab路径、对象名称或本地数组下标。

### 6.2 PlayerCommand

包含：玩家槽位、模拟刻、命令序号、量化移动向量、技能相位、量化瞄准数据和取消标记。命令必须可被本地输入、AI和网络重放共同生成。

### 6.3 战斗快照

快照按配置频率发送，包含需要校正的权威状态，例如角色位置/速度、生命、能量、倒地状态、Boss阶段和关键实体状态。渲染帧率与网络刻频率分开；具体频率由 `NetworkTuningConfig` 决定，不写死在代码。

### 6.4 事件

一次性事件包含技能确认、伤害、清弹、掉落、阶段切换、救援和章节结束。每个事件有唯一序号，客户端必须去重，防止重发造成双倍伤害或重复奖励。

## 7. 移动与延迟处理

- 本地玩家移动先在本机预测，避免每次按键都等待网络往返。
- 主机使用同一移动算法验证并模拟。
- 客户端收到权威位置后，小误差平滑修正，大误差直接纠正并记录诊断。
- 远端角色使用插值，不对旧快照直接瞬移。
- 技能消耗和伤害不由客户端预测为最终结果。
- Harness瞄准圈完全本地流畅移动；释放请求到达主机后才生成权威清算领域。

这不是严格锁步游戏，不要求所有粒子和所有普通弹在两台设备像素一致；要求玩法结果由主机一致裁决。

## 8. 同伴AI与联网共用

每个角色槽位在任意时刻只有一个 `ICommandSource`：

- `LocalInputCommandSource`
- `RemoteCommandSource`
- `CompanionAiCommandSource`
- `ReplayCommandSource`（测试/回放预留）

控制权切换只替换命令来源，不替换角色GameObject，不重新生成角色，不清空生命、能量、Buff和冷却。客户端重连后也通过同一机制从AI交还真人。

## 9. 在线安全和容错

本项目不是竞技游戏，不投入重型反作弊，但仍需防止错误数据破坏房间：

- 主机校验移动范围、技能状态、能量、冷却、角色槽位和命令序号。
- 客户端不能上传“造成多少伤害”或“清除了哪些弹”的最终答案。
- 网络消息限制长度和频率，未知ID直接拒绝并记录。
- 不在日志中写房间令牌、完整IP或平台身份凭据。
- 重复包、乱序包和超时必须有确定处理规则。

## 10. 网络服务抽象

至少分为：

- `ISessionService`：创建、加入、离开房间，维护成员和准备状态。
- `IRelayService`：申请/加入中继，返回连接参数。
- `ITransportAdapter`：把连接参数交给底层传输。
- `INetworkClock`：提供模拟刻和延迟估计。
- `IVersionCompatibilityService`：判断客户端、内容和协议是否兼容。

开发顺序依次是：本机Host → 同机客户端测试 → 局域网直连 → 公网中继。不能在本地战斗还未一致时，用公网服务掩盖同步错误。

## 11. 资源热更新结构

### 11.1 包内最小内容

安装包必须包含：

- 启动场景和更新界面。
- 更新服务、资源服务和错误提示所需代码。
- 最低可用字体、UI、占位图和离线提示。
- 一份可离线启动的基础内容版本。

即使更新服务器不可达，玩家也应能选择使用已验证的本地旧版本进入游戏；只有协议不兼容的强制在线模式例外。

### 11.2 可更新内容

- 角色/Boss/背景/UI Sprite与动画。
- 音效、音乐、Timeline和VFX Prefab。
- 章节定义、敌人定义、弹幕Pattern和数值配置。
- 本地化表和图鉴文本。
- 后期接入后的热更新程序集及其补充元数据。

### 11.3 更新流程

```text
启动
→ 读取包内版本与本地缓存
→ 请求远端版本清单
→ 校验客户端基础版本/协议版本
→ 下载新清单
→ 计算缺失资源和空间
→ 用户确认下载（可配置阈值）
→ 下载到临时区
→ 校验大小、哈希和依赖
→ 原子切换有效版本
→ 初始化内容
→ 进入主菜单
```

下载中断不能覆盖最后一个可用版本。只有新版本全部校验成功后才切换；启动崩溃或初始化失败时允许回退到上一份完整内容清单。

## 12. 三种版本号

- `ClientVersion`：APK/EXE基础程序版本。需要原生插件、AOT代码或Player Settings变化时必须发新安装包。
- `ProtocolVersion`：联机消息契约版本。不兼容时禁止进入同一房间。
- `ContentVersion`：图片、音频、配置、关卡和热更新程序集版本。

三个版本不能混用。仅更新一张背景图不应强迫玩家更新APK；修改网络消息结构也不能只改内容版本假装兼容。

## 13. 配置热更新规则

- 远程配置有Schema版本、稳定ID和完整校验。
- 进入章节时把本次使用的配置复制为只读运行时快照；战斗中下载的新配置不修改当前局。
- 联机双方不各自读取本地伤害数值；主机使用房间锁定的内容版本裁决。
- 删除旧ID前必须确认没有存档、章节或网络消息仍引用它。
- 配置错误时拒绝启用该内容包，并回退，不使用代码里藏着的默认玩法值。

## 14. C#代码热更新边界

计划接入HybridCLR时，代码分为：

- **AOT基础层**：启动、更新、资源接口、联网协议基础、安全校验、平台桥接和热更新加载器。改变它通常需要新安装包。
- **热更新玩法层**：具体角色策略、敌人、Boss、章节流程和UI业务。满足兼容规则时可下载更新。
- **共享契约层**：稳定ID、序列化数据和接口。任何破坏性修改都要提高协议/Schema版本。

接入HybridCLR前必须完成：Windows与Android IL2CPP构建、资源更新闭环、程序集边界测试和回滚测试。不得一开始就把所有代码放入热更新程序集。

## 15. 服务器与发布现实

公网好友房间至少需要“帮助双方找到彼此”的房间服务；多数家庭网络还需要中继才能可靠连接。热更新还需要可通过HTTP访问的清单和资源文件。

因此最终部署至少包含：

- 静态资源存储/CDN或普通HTTP文件服务器。
- 房间/邀请服务。
- 中继服务或可替换的打洞/转发方案。

项目代码可以完全开源、游戏可以免费，但公网服务仍可能产生域名、流量和服务器费用。开发期先保持适配器可替换，不预先绑定必须付费的平台。

## 16. 测试矩阵

### 16.1 联机最低测试

- 房主DeepSeek/客人Harness，以及角色互换。
- Windows↔Windows、Windows↔Android、Android↔Android。
- 低延迟、延迟波动、丢包、客户端短时断网和客人主动退出。
- Harness在同一模拟刻清弹与Boss切阶段。
- 玩家倒地同时断线，AI接管不能重复生成角色。
- 掉落被双方同时拾取只结算一次。
- 同一技能请求重复到达只消耗一次能量。

### 16.2 热更新最低测试

- 无网络使用本地完整版本进入单机。
- 下载中断后续传或安全重试。
- 哈希不匹配拒绝切换。
- 空间不足在下载前提示。
- 更新后联网版本检查正确。
- 新版本启动失败能够回退。
- Android杀进程重启不会留下半份有效内容。

## 17. 首次实现边界

网络和热更新从架构第一天被考虑，但实际接入顺序不能颠倒：

1. 统一命令和权威战斗模型。
2. 本机双角色与同伴AI。
3. Host/Client本机测试。
4. 局域网直连。
5. 公网房间与中继。
6. 资源热更新。
7. C#代码热更新。

每一步通过自动测试和人工验收后再进入下一步。这样不是把联网“留到最后”，而是先完成联网真正依赖的战斗边界。
