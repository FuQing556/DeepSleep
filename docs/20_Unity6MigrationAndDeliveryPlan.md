> 最后更新：2026-09-04  
> 状态：执行权威；Unity 6.6 新工程 U0 与首次本地仓库基线已完成，下一阶段为 U1  
> 目标编辑器：Unity 6.6（6000.6.0f1，Hub推荐的正式受支持版本）
> 目标模板：通用二维（Universal 2D），使用URP 2D Renderer

## 1. 当前真实起点

- 当前工作工程为 Unity `6000.6.0f1` 创建的 Universal 2D 新工程，路径为 `D:\Unity Work\DeepSleep_Unity6`。
- U0 已由用户实际验收：编辑器诊断脚本成功执行，活动构建目标为 `StandaloneWindows64`，Console 为 0 Warning、0 Error，Visual Studio 2026 联动正常。
- Unity 模板现有 `Assets/Scenes/SampleScene.unity`；`Assets/Settings/Scenes/URP2DSceneTemplate.unity` 是场景模板源文件，不是第二个游戏关卡。
- Input System `1.20.0` 已随模板安装，但正式玩法 Input Actions 尚未创建。
- 尚未重建逻辑 16:9 相机、Physics Layers、Sorting Layers、正式 Gameplay 场景和程序集定义。
- 尚无玩家移动、战斗、联网、热更新和玩法 Prefab 代码。
- 当前目录已初始化 Git `main` 分支、Git LFS 与 GitHub `origin`，首次本地基线提交已完成但尚未推送；旧工程继续完整保留。

## 2. 执行原则

1. 用户负责所有Unity编辑器操作；Agent负责编写代码、测试、配置结构、验证器、素材和逐步说明。
2. 不手写场景、Prefab、Input Actions、程序集定义和Project Settings。
3. 玩法数据不写死在代码中；所有调参进入配置资产。
4. 不用 `AddComponent`、`RequireComponent`、Find、Resources路径和隐式装配。
5. 每轮只改一个小系统；用户确认Unity编译与Play Mode结果后再继续。
6. 联网和热更新是架构目标，但不允许先安装所有包再寻找用途。

## 4. U0｜Unity 6.6新工程门禁

技术上Unity可以原地升级旧项目，但本项目没有玩法代码和Prefab，输入又已因玩法改版失效。新建工程只需重做少量基础设置，却可以避免携带Unity 2022包锁定、旧输入、错误程序集名称和无效设计痕迹，因此锁定为新建方案。

### 4.1 保留与不迁移

旧工程目录在新工程验证前完整保留，不删除、不覆盖。

后续迁入：

- `docs/`全部设计、参考图和候选素材。
- 用户已确认且仍符合新规格的正式美术源文件。
- 经逐项检查后仍有价值的工具脚本；不能整目录盲拷。

不迁入：

- `Library/`、`Logs/`、`Temp/`、`Obj/`、`.csproj`、`.sln`。
- 旧 `Packages/` 与 `ProjectSettings/`。
- 旧 `DeepSleepInput.inputactions`，因为动作语义已失效。
- 旧程序集定义，避免把内部名称和旧引用带入新工程。
- 未经核对的 `.meta`；正式进入新Assets目录的文件由新工程生成并稳定管理元数据。

### 4.2 创建步骤的拆分原则

用户安装Unity 6.6后，实际操作仍拆成独立小步：

1. 用Unity Hub新建一个Unity 6.6（6000.6.0f1）的通用二维（Universal 2D）项目，路径不得位于旧Unity项目内部。
2. 第一次只确认新项目能打开、保存、关闭、重开且Console无红错。
3. 回报准确Unity补丁版本、新工程绝对路径和使用的2D模板名称。
4. 下一轮才决定最终项目路径与文档迁入方式。
5. 再逐项重建Gameplay场景、相机、图层、排序层、Input System和程序集；每项都重新验收，不复制旧设置文件。

U0不安装Netcode、YooAsset和HybridCLR。新工程基础状态未通过时禁止叠加第三方问题，也不要求现在复制任何旧素材。

## 5. U1｜输入与命令

- 用户在Input Actions编辑器中把旧动作改为 `Move/PrimarySkill/SecondarySkill/Aim/ConfirmAim/CancelAim/Pause`。
- Agent先实现不依赖具体设备的 `PlayerCommand`、命令源接口和测试。
- 再实现Input System适配器，把Actions读取为命令。
- 触摸UI适配器后做，但不得复制角色移动代码。
- 验收只看命令数值和相位，不生成玩家Prefab。

## 6. U2｜双角色移动

- `PlayerMotorConfig`保存速度、加减速、边界响应和校正参数。
- 两个灰盒角色使用相同移动算法与不同配置资产。
- Rigidbody2D、Collider2D和渲染子节点由用户显式装配。
- 玩家之间不发生实体阻挡；各自仍与玩法边界和可碰撞环境正确交互。
- 同时验证16:9、20:9与16:10视图，玩法判定区保持一致。

## 7. U3–U5｜本地合作战斗

### U3 蓝鲸

- 目标查询、自动索敌、饭团对象池、真实阻挡、集中检索和护航。
- 至少三档可见火力成长。
- 性能测试关注满级饭团数量和每帧分配。

### U4 Harness

- 本地流畅选区、释放合法性预览、预算消耗、清弹查询和范围伤害。
- 明确区分可清除/不可清除弹。
- 空放、取消、能量不足和目标超界都有确定反馈。

### U5 合作闭环

- 独立生命、故障核心、救援、共享共鸣和组合技。
- 灰盒波次必须迫使两种职责都出现。
- 不在此阶段制作正式章节时间轴。

## 8. U6｜同伴AI

- AI只产生 `PlayerCommand`，不直接控制Transform或调用技能组件。
- 先用录制的威胁场景测试避弹、清弹、压火和救援。
- DeepSeek AI与Harness AI分别有战术配置。
- 玩家角色互换后重跑同一套测试。
- AI接管/交还不能重建角色或丢失本局状态。

## 9. U7｜灰盒Boss纵切面

只制作一个无正式角色美术的Boss，验证：

- 一段适合蓝鲸持续压制的目标阶段。
- 一段适合Harness高价值清弹的危机阶段。
- 一段清弹成功后共同爆发的破绽阶段。
- 双人真人、DeepSeek+Harness AI、Harness+DeepSeek AI三种组合都能完成。

灰盒Boss通过后，才允许把完整章节和正式Boss素材接进来。

## 10. N0–N2｜联机

### N0 同机网络

- 安装并锁定Netcode for GameObjects与Unity Transport兼容版本。
- 一台电脑启动Host和测试客户端，两个槽位分别接收本地与远端命令。
- 先同步移动和角色选择，再逐个加入伤害、弹幕、掉落、AI接管和Boss。

### N1 局域网

- 两台设备通过直接地址连接。
- 完整通过灰盒Boss，不依赖大厅或中继。
- 注入延迟、丢包和断开，验证去重、校正和AI接管。

### N2 公网

- 先做网络服务可达性验证，再确定Unity服务或其他国内可用方案。
- 先实现跨端私人房间码、准备、版本检查、中继和错误分类；验证电脑↔手机、电脑↔电脑、手机↔手机。
- 私人房间稳定后，再实现“先选角色、后排队”的快速匹配，匹配器只配对互补角色。
- 不做主机迁移；房主退出结束房间。

## 11. H0–H1｜热更新

### H0 资源

- 在Unity 6.6和目标平台上验证并锁定YooAsset版本。
- Agent实现项目自己的更新/资源接口和启动状态机。
- 用户配置资源分组、远程地址和构建流程。
- 依次测试：无更新、有更新、断网、中断、损坏、空间不足、回退。

### H1 代码

- Windows和Android先能稳定完成普通IL2CPP构建。
- 接入并锁定HybridCLR版本。
- 拆分AOT基础层、共享契约层和热更新玩法层。
- 先热更一个无网络契约变化的小功能，再测试联网兼容与回滚。
- 任何协议破坏性变化仍要求提升协议版本，不能靠代码热更强行混房。

## 12. C0之后的内容生产

每章按相同门禁推进：

1. 机制灰盒和合作职责通过。
2. 标准难度可由真人双人和两种单人组合完成。
3. Boss时间轴、掉落和失败提示完整。
4. 再制作/接入正式角色、背景、VFX、UI和音频。
5. Windows与Android性能、触摸、安全区和联网回归通过。
6. 加入热更新内容包，验证旧客户端兼容或明确阻止进入。

现有素材全部保留。旧山体、气泡、障碍和非循环背景可转为遮挡、前景、章节卡或事件装饰，不因玩法改版删除。

## 13. 发布闭环

- Windows x64：可解压运行的ZIP、版本说明和校验值。
- Android：签名APK、最低系统版本说明和安装说明。
- 热更新：对应客户端版本的内容清单、资源包、回滚版本和发布记录。
- 公网服务：房间/中继环境配置与隐私说明。
- 开源仓库：不提交密钥、签名私钥、服务器令牌和个人配置。
- 本地存档：单机与联机完成记录、设置、图鉴和章节解锁；首版不做云存档。

## 14. 下一步

U0 与首次本地 Git 基线已完成，尚未推送。下一步进入 U1，第一小步只实现不依赖设备的 `PlayerCommand`、`ICommandSource` 与对应纯 C# 测试，不同时创建 Input Actions、移动组件或安装联网/热更新包。
