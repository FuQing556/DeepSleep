# 单关卡管理架构与内容接入规范

日期：2026-10-05。范围：所有玩法关卡，不是某一关的内容方案。

实际源码地图、共用范围和维护问题见根目录 [PROJECT_STRUCTURE.md](../PROJECT_STRUCTURE.md)。本篇保留目标架构与落地记录，不代替当前结构地图；已跑通流程不代表冗余和职责交叉已经消除。

状态：**A 批已迁移；当前战斗循环的 B 批生命周期修复已装配、验证并收尾。** 任意任务/阶段、模块检查点、C/D 环境交互及制作窗口仍是后续能力，不代表已实现，也不自动成为下一项内容任务的前置改造。当前实现范围见第 12—13 节；不打包。

用户要求统一管理“怪物如何加入、场景如何管理与变化、后续交互如何接入”，而不是规定一关几个区域、几张背景或几次休息。此前助手提出的固定数量方案不作为本架构或内容制作的依据。

## 1. 要解决的问题

以后制作一关，应有一个明确入口，能看到它使用的流程、怪物、遭遇、场景表现、交互和任务。加入已有内容主要改配置；新增行为只编写该行为及其适配器、测试，不到章节、AI、清场和网络核心中反复加敌种或关卡分支。

采用“**一个关卡定义、一次内容登记、一套显式装配、一个流程推进者**”。不另造一个与现有 `ChapterRunController` 争夺推进权的万能 `LevelManager`。

这里的“关卡”是一局的内容与结算单位；“阶段”是关内流程步骤；“Unity 场景”是对象容器；“背景状态”是表现方案。这四者不能混用：切背景不等于加载场景，刷怪结束也不自动等于阶段完成。

## 2. 现有能力与缺口

| 领域 | 已有实现 | 尚缺的管理能力 |
|---|---|---|
| 关卡入口 | `MetaLevelDefinition` 统一引用身份、场景、奖励、流程配置和普通敌人清单；校验启动/场景/结算身份 | 环境、交互、通用任务尚未纳入内容清单 |
| 关内流程 | `ChapterRunConfig`、`ChapterRunController` 管段落、计时、失败、重试和结算 | 配置目前是战斗段列表，休息流程隐含在控制器协作中；不能直接配置任意类型阶段 |
| 普通怪物 | Actor、Pool、Binder、Director、Channel 可复用；清单与绑定表驱动显式派生接线 | 仍需显式制作/放置运行模块；完整添加/移除 UI 和多弹池复制未完成 |
| 特殊遭遇/任务 | `IChapterCombatObjective`；豆包独立驱动接入章节 | 接口只有适用段、完成、重置；缺通用失败、可选目标与恢复契约 |
| 场景表现 | 有循环背景、有限全景、镜头合成和部分节点过渡 | 没有关卡级环境状态目录、进入/切换/恢复管理；节点还直接持有背景引用 |
| 交互 | 节点热点、升级、准备/出门已实现 | 类型、提示和执行集中在节点枚举与 switch；不是通用交互入口 |
| 生命周期 | Chapter 统一现有开段/节点/重试，World 从 Bindings 清场，特殊模块显式停止，Router 退出契约 | 任意新模块的初始化/快照恢复/释放契约并非全部已有 |
| 校验 | `GameplayFoundationAudit`、构建门禁，已补清单、派生数组、战斗域/参与者和关卡身份检查 | 通用环境/交互/任务/检查点模块未实现，不能声称这些内容已能自动验收 |

结论：普通敌人登记已有统一来源，其他内容管理仍待迁移；不能因已有基础审计通过，就称“后续随便加内容都不会漏接”。

### 核实到的具体缺陷与限制

- **关卡身份错绑已修：** 迁移前 `World01_EarlyInternet` 的 `_level` 指向 `PrototypeSky`；现已显式绑定 World01，启动、场景与结算均校验同一关卡定义，运行时不自动覆盖错误引用。两关各自拥有流程配置副本，未改变原段落数值，也未修改或补偿用户历史存档。
- **当前清场职责已迁移并验证：** `ChapterCombatWorld2D` 读取关卡绑定的普通敌池/弹池/刷怪器，豆包显式参与停止。节点不再保存这些数组。已测自然清场中的奖励/失败和强制回收无奖励，见第 13 节。
- **敌弹复制入口仍为单池：** `NetworkWorldSnapshotChannel.EnemyBullets` 是单个弹池。多种射击怪若使用不同弹池，不能只往 `EnemyPools` 加项就认为联机接入完成。
- **目标表达受限：** 当前战斗段要求正时长和正击败数，章节在计时到达后判断击败数及附加目标，不是“任意目标达成便提前结束”。纯交互、护送或纯 Boss 完成条件需要扩展，不能假装配置已支持。

## 3. 目标结构：定义、装配、运行分开

以下为整体目标结构。已实现定义对流程/普通敌人清单的引用、场景绑定及现役战斗的停止契约；环境、交互、任意任务和任意模块的快照恢复仍属于后续能力。

```text
MetaLevelDefinition                    唯一关卡入口：身份、场景、奖励
├─ ChapterRunConfig                    阶段顺序、完成/失败策略、内容启停引用
└─ LevelContentManifest（新增）          本关可使用的敌人、遭遇、交互、环境定义
                 │
       显式 Editor 装配与只读审计
                 ↓
LevelSceneBindings（新增）              定义与场景实例/服务/锚点的绑定
                 ↓
ChapterRunController                   唯一决定阶段进入、完成、失败、重试、结算
├─ 刷怪/遭遇模块                        执行玩法，报告事实
├─ 任务与交互模块                       校验请求、报告进度/结果
├─ 环境表现模块                         按权威阶段状态播放、切换、恢复
└─ 生命周期与检查点协调                 调用模块停止、清理、恢复；不另持阶段状态
```

### 3.1 配置的唯一来源

- 扩展 `MetaLevelDefinition` 引用 `ChapterRunConfig` 和 `LevelContentManifest`，不再创建另一个独立保存关卡 ID/奖励的平行定义。
- `ChapterRunConfig` 继续作为流程配置入口。目标是显式阶段列表：每项有稳定 `PhaseId`、阶段类型、参数、完成/失败策略、启用内容及环境状态引用。现有战斗参数作为战斗阶段的配置复用；休息阶段由现有节点功能执行。先迁移现有行为，再增加新类型；不并行保留两套可编辑流程表。
- `LevelContentManifest` 登记本关能用什么；阶段列表选择何时启用什么。仅登记不会自动开刷、显示交互或切背景。
- 共享内容定义保存 Prefab、配置与能力声明；关卡条目保存本关启用的模块、参数覆盖和锚点键。场景实例引用只在 `LevelSceneBindings`，不放进共享 ScriptableObject。
- ScriptableObject 不保存当前血量、阶段进度、交互已消费状态等本局数据；进入关卡后固定本局配置，运行状态在实例中。

### 3.2 场景绑定与派生清单

`LevelSceneBindings` 显式引用本关定义、章节控制器、节点控制器、固定步、会话、权限门、感知/障碍注册表、奖励、环境根、内容实例和命名锚点。它只做绑定与启动校验，不计时、不判输赢、不推进阶段。

内容条目有稳定 `EntryId`。绑定表只回答“这个条目对应场景中的哪组实例”，不再独立决定启用哪些内容。Editor 装配工具据此生成现有消费者需要的数组；这些数组是**派生接线结果**，不是第二套人工维护的内容来源。手工改动造成不一致时，审计报错，不在 Play 时悄悄修正。

首批限定一个敌人池由一个刷怪频道管理；同敌种多位置生成优先使用该频道的锚点组，确需独立频道时使用独立池并计入容量/复制预算。现有 Director 按整个池的 `ActiveCount` 判断上限，回收事实也不带频道归属，不能直接宣传共享池支持独立频道限额。未来开放跨频道共享池前，必须明确共享总预算、出生归属和任务/清理语义，并增加相应契约与测试。模拟依赖顺序显式声明，不靠 GameObject 名称排序决定逻辑先后。

### 3.3 ID 与职责边界

| 标识/持有者 | 用途与限制 |
|---|---|
| `LevelId` | 关卡身份与通关存档；入口、场景绑定、结算必须一致 |
| `PhaseId` / `EntryId` | 关内阶段/内容条目的稳定身份；不用数组位置或对象名称作为持久身份 |
| 敌人内容 ID / `EnemySpawnChannelDefinition` | 前者识别可复用敌种，后者识别刷怪通道；不能与实体出生 ID 混用 |
| 运行实体 ID / 运行代次 | 区分本次出生及重试前后对象；网络、延迟回调不能作用到旧实例 |
| `ChapterRunController` | 唯一推进关内流程；模块只能上报结果或请求，不直接改当前阶段 |
| `RestNodePrototypeController2D` | 目标收敛为节点局部显现、交互区、准备与离场表现；不再兼任全关内容登记中心 |
| `GameSceneRouter` | 仍是唯一实际 Unity 场景切换与退出入口 |

## 4. 新怪物怎么加

### 4.1 把已有怪物加入另一关

1. 在该关内容清单中选择敌人运行模块，设置条目 ID、刷怪频道、配置覆盖和生成锚点。复用已有敌种，不复制战斗逻辑。
2. 在相应阶段启用频道并配置日程、存活上限等。沿用 `SegmentSpawnRule` 的频道资产匹配，不按名称猜类型。
3. 通过显式装配工具把运行模块放入本关绑定根，接入下表各消费者；预览差异后应用，再做只读审计。
4. 跑完整生命周期回归。通过后，该关才算接入，而不是“场景里能刷出来”就完成。

### 4.2 增加一种新行为怪物

1. 制作敌人 Actor Prefab：生命、运动、受击、攻击、视觉与感知组件显式装配；新增行为写在自己的固定步策略和配置中。
2. 制作/扩展可复用运行模块 Prefab：Actor 池、Director、频道、场景依赖 Binder；需要敌弹或专属反馈时同时声明其池与复制方式。已有 404、机械蛇运行 Prefab 可以参考，但当前原始 Prefab 仍需要补频道/感知等场景依赖，并非拖入即用。
3. 声明模拟归属、奖励/击败计数、清理范围、AI 可见几何、联机权限与表现依赖，再走 4.1 的关卡登记流程。
4. 新行为不能通过在章节控制器里写 `if (敌种 == ...)` 接入；特殊遭遇由独立驱动模块适配章节目标。

### 4.3 一次登记必须覆盖的接线

| 能力 | 现有消费者与约束 |
|---|---|
| 生成与计分 | 章节的 Director/Pool、阶段频道规则；自然离场/清场不冒充击败 |
| 模拟 | `FixedSimulationLoop.worldStepComponents`；Actor 内部步骤由池→Actor 推进，不能又登记到全局重复执行 |
| 清场 | `ChapterCombatWorld2D` 直接读取 `LevelSceneBindings.Enemies`，特殊模块显式登记 `ParticipantComponents`；节点不再维护全关池列表 |
| 奖励 | `EnemyTokenRewardController`；依照回收原因及奖励抑制标志，清场不发奖励 |
| AI | 普通目标进入感知注册表；危险障碍进入障碍注册表，不能把所有机关都当可攻击敌人 |
| 联机模拟 | `NetworkAuthorityGate` 禁用客机权威逻辑；不把特效/跳字等纯表现放入禁用列表 |
| 联机表现 | 世界快照敌池、弹池、镜像容量、全部可能使用的 Sprite；特殊状态用明确的复制适配器 |
| 专属效果 | 本地表现池、必要的网络事件与稳定效果 ID；不依靠客机重复执行伤害触发效果 |

新射击怪若与现有敌弹池兼容，可以明确共用；需要不同弹池时先补显式多弹池复制与测试，不暗中漏同步。新消息经过 `NetworkMessageCatalog`，不直接随手分配消息号。

必须验证：生成→运动/攻击→命中/死亡→计数/奖励→越界/碰撞离场→切段/失败清场→再次出池状态恢复，以及主客机权限、AI 接管、命中特效和伤害数字。池容量应同时覆盖各阶段的峰值组合，不能只测试一种怪物单独运行。

## 5. 场景怎么管理、怎么变化

### 5.1 容器与内容分层

默认一个关卡使用一个 Gameplay Unity 场景作为容器，按显式绑定组织：共享服务、玩法实体/碰撞与锚点、遭遇/交互模块、环境表现、相机/UI。这个默认值是装配方式，不限制关卡内容规模或背景数量。

同一关内环境变化通过环境状态和内容模块切换，正常情况下不 `LoadScene`。具体图片张数、循环/有限全景、各阶段构图由关卡自身配置，不上升为全项目定额。

如果未来确实需要分区流式加载，另加内容加载适配器和准备/释放契约；不把当前带场景引用的 Session 直接常驻。当前实际跨 Unity 场景会结束房间，保持连接跨场景尚未实现。

### 5.2 环境状态

目标环境模块接收 `EnvironmentStateId`、阶段时间与过渡上下文，管理背景/前景层、光照/色调、装饰特效、声音及切换方式；只播放表现，不判断任务完成。

- 阶段配置明确“进入时切到哪个状态”和“阶段内哪些参数可连续变化”。切换时点与变化曲线分开，不用背景动画播完去偷推关卡。
- 有限全景继续复用 `FinitePanoramaLayer2D` 的覆盖/位移约束；循环背景作为另一种明确策略。两者不是环境状态机本身。
- 环境模块拥有背景层变换；相机仍由现有统一镜头合成器写入，禁止多个组件抢写相机。
- 玩法碰撞、刷怪点、机关和传送门使用独立配置与锚点，不能从背景 Sprite bounds 推导。更换纯视觉状态不改变玩法边界。
- 若一阶段确实更换物理布局，将其作为玩法模块停用/清理/重新启用，而非纯背景切换；必须校验玩家与实体不会落入新障碍，并明确迁移规则。
- 手机更宽时可以看到电脑看不到的两侧装饰。覆盖校验包含支持宽高比、前视、震屏和背景自身位移；UI 的全屏装饰、居中内容和安全区操作独立，不整体跟随画面扩展偏移。
- 纯装饰不逐帧同步 Transform。权威端同步环境状态及必要时间基准，客机本地播放；加入/重连需要当前状态基线，不能只靠一次性切换事件。
- 重试恢复对应阶段的环境基线并取消旧过渡；退出释放旧回调、声音和临时表现。具体太阳/耀斑等内容不在此补定或制作。

## 6. 新交互怎么加、怎么管理

把交互拆为“可交互对象/触发范围”“请求校验与结果”“本地提示表现”。节点只是交互的一种使用场景，不把后续宝箱、开关、NPC、机关都塞进节点枚举。

目标接入流程：

1. 制作交互定义：稳定条目 ID、处理器类型的显式引用、允许阶段/角色、触发方式、重复/一次性规则、消耗与奖励、状态保留范围。类型用明确代码/资产引用，不反射字符串创建行为。
2. 制作组件/Prefab：显式范围、交互锚点和视图。已有处理器可以只换配置；全新行为增加独立处理器及测试，不修改节点的大 switch。
3. 登记到本关内容清单并绑定实例，在阶段中指定何时启用。UI 从可用性结果显示提示与拒绝原因，不直接修改钱包或流程。
4. 按“命令请求→权威校验→一次提交→结果事实→表现/任务消费”的路径执行。校验包括角色所有权、对象存在、阶段、距离、成本、已消费状态和请求去重；失败不部分扣费或发奖。
5. 明确进出范围、暂停、重试、断线、禁用/销毁时如何取消；对象回池必须清理占用、订阅和已执行状态。

仅打开本地说明等无玩法影响的交互可以本地处理；改变关卡、生命、资源、奖励或共同机关状态的交互由房主裁决。两人同时操作一次性对象只能成功一次；客机收到重复结果不能重复扣费/发奖。

真人输入与 AI 应调用相同的请求校验入口。AI 是否主动操作属于独立策略与授权，不因接入统一接口就自动购买、选奖励或点准备。AI 的“能进入并停稳”的目标区域与 UI 热点判定分别表达；迁移不擅改当前碰撞体或根点占用规则。

交互状态明确属于：本次激活、当前阶段检查点、整局、永久档案之一。禁止用未清理的静态布尔值跨关保存。永久档案变更走现有档案服务与结算边界，不由交互视图直接写盘。

## 7. 任务与关内流程

任务是“结果是否满足”的规则，不是交互按钮本身。击败某类敌人、抵达区域、启用开关、护送目标和完成遭遇，都可以向任务报告类型化事实。

目标任务配置显式描述：适用阶段、必需/可选、完成条件、失败条件、进度状态及重试策略。阶段完成策略区分计时结束判定、目标完成即结束、等待外部流程等；不能硬塞虚假的击败数来适配纯交互任务。

`ChapterRunController` 汇总当前阶段的结果，执行唯一一次状态提交。遭遇和交互模块不直接调用下一关、结算或修改全局时间。重复事实、同一步完成/失败并发要有确定的去重与优先级；迁移先保持现有结果顺序，再为新阶段类型增加规则与测试。

现有 `IChapterCombatObjective` 和豆包驱动先作为适配层保留，之后扩展任务结果契约；不把豆包专用逻辑搬进公共章节控制器。流程配置先支持明确顺序，不为尚无需求的复杂分支额外搭建图编辑器或脚本语言。

## 8. 初始化、切换、检查点与退出

每个内容模块需声明职责与参与的生命周期；不要求纯背景也实现战斗、奖励等无关接口。接口按能力拆分，不做所有方法都空实现的万能基类。

| 时点 | 统一要求 |
|---|---|
| 进入关卡 | 验证启动定义与场景绑定一致，检查所有依赖与内容版本；缺失时明确阻止开战，不临时创建替代组件 |
| 初始化 | 显式注入依赖、预热池、建立订阅；服务就绪后才能启用玩法模块，不靠 Awake 顺序碰运气 |
| 进入阶段 | 控制器选定阶段，应用环境基线/目标/交互/刷怪规则，最后开放模拟与输入 |
| 自然清场 | 先停止新生成，保留残敌战斗、必要模拟和正常击败奖励；清场条件满足后才停止攻击、回收临时表现、结束阶段订阅。不能提前封锁攻击导致残敌无法清除 |
| 强制停止 | 失败重试/整关退出先阻止新生成、新交互和新攻击，取消待执行动作，再通过模块回收契约清理实体与临时效果、更新感知/障碍可用性，释放阶段临时订阅；强制回收不产生击败奖励 |
| 重试 | 停止旧代次，验证并恢复检查点参与者，重置阶段临时状态/环境/任务，全部就绪后恢复模拟 |
| 退出关卡 | 模块停止后仍经过 Router/Session 既有退出链；等待传输关闭和旧根销毁，不绕过它直接 LoadScene |

同一个模块只能有一个模拟驱动者：直接由 `FixedSimulationLoop` 调用，或由其所属驱动调用，二选一。阶段切换、回收、取消和释放应可重复调用而不重复奖励、不泄漏订阅。

注册与订阅按所属生命周期释放，不能每次停阶段就全部注销。现有普通敌人的感知在池创建 Actor 时注册，回池后由 `IsObservable` 过滤，直到销毁才注销；它不是每次 Rent 都重注册。此类池实例登记、池的回收事件订阅保留到池释放；阶段临时监听随阶段结束释放；危险物按自身既有出入池契约成对登记/撤销。若改变这些归属，必须同步补上重新激活后的恢复路径并测试复用，不能导致下一次出池永久丢失感知或奖励监听。

当前检查点只覆盖玩家位置/生命、节点升级与钱包等特定数据，不是整个世界的快照；整局累计统计也不等于段内回滚数据。目标是在现有检查点边界登记需要恢复的模块，各自提供带身份/版本的快照；先验证整组数据，再提交恢复，失败保持暂停并报告原因，不能半恢复后继续。

模块必须声明“重建”“恢复快照”或“整局保留”，不能默认把所有对象存档。迟到网络包、协程和回调要校验运行代次与条目身份，不能让失败前的开门/奖励回调污染新阶段。检查点支持不代表新增中途退出续玩或主机迁移，这些能力不在本次默认范围内。

## 9. 统一制作入口与自动检查

目标新增 `LevelAuthoringWindow` 与显式装配工具，入口围绕选中的关卡，而不是为每一关新增一个写死路径的 `InstallAll`：

1. 选择/创建关卡定义，查看流程和内容登记。
2. 添加已有怪物、遭遇、环境或交互，填写本关参数与锚点映射。
3. 预览待创建对象、引用接线和会受影响的派生列表；用户修改的碰撞体、素材和配置不能被默认值覆盖。
4. 明确执行 Unity Editor API 装配，限定当前目标场景/关卡所属资产，保留 Undo/变更记录。反复应用无重复组件、条目或订阅；移除内容先报告使用者和影响，不删除共享资产或非工具拥有的对象。
5. 运行只读审计与对应回归，生成可追溯报告。校验与应用是两个独立动作；OnValidate、打开窗口和进入 Play 都不能自动修场景。

既有安装器只复用其中安全的装配方法，不直接批量重跑。原因：有的遇到现有组件便返回，有的重写原型段落，有的按名称/路径猜敌种，有的仅支持两个固定场景。这些不是通用内容管理入口。

新增校验并入 `GameplayFoundationAudit` 及其构建门禁：

- 定义/场景/启动/结算身份一致；运行模式下有启动上下文则严格匹配；Editor 直接打开场景测试使用明确绑定，不暗退原型关卡。
- 阶段、内容、频道与锚点引用有效、ID 唯一；目标可表达且有可完成路径；停用/移除条目不存在悬空引用。
- 登记内容与模拟、章节计数、奖励、清场、网络、权限、AI 等消费者集合一致；合法共享依赖只登记一次。
- 纯表现不被权威门禁关闭；多弹池及特殊机制有明确复制策略；初始和所有可切换 Sprite/效果都有合法目录项。
- 生命周期/检查点参与者完整；固定步不重复驱动；依赖顺序与池/镜像/消息容量满足声明的峰值。
- 环境覆盖手机宽屏和镜头预算；交互范围/玩法边界来自独立锚点与几何，不由美术尺寸推导。

诊断应给出关卡 ID、条目 ID、对象路径、缺失字段和修复入口；审计发现缺失即失败，不扫描后自动补好。运行时保持显式引用；Editor 可以只读检查层级，不用名称猜测作为权威登记来源。

## 10. 实施顺序与完成标准

按依赖分批接入，但每批都遵守上面的整体边界；不是把一份文档写完就宣布架构已经落地。

| 批次 | 实施内容 | 完成判据 |
|---|---|---|
| A：身份与登记 | 修关卡身份错绑和校验遗漏；扩展关卡定义，加入内容清单/场景绑定；集中派生现有登记数组；明确多弹池策略 | 两现有场景玩法不变；加/删已有敌模块不再手改多份数组；重复应用无变化；故意漏清场/错关卡引用可被阻断 |
| B：流程与生命周期 | 在现有章节控制器内统一阶段进入/退出/重试；把节点的全关管理职责移交统一登记；显式化当前战斗/休息流程与任务策略 | 当前通关/失败/节点/钱包回滚行为保留；自然清场仍可击败残敌，强制回收不产生击败奖励，无旧实体/回调残留；新任务不添加关卡专用分支 |
| C：环境与交互 | 环境状态控制和恢复；拆出通用交互请求/处理器/视图；迁移现有升级与出口 | 现有交互语义不变；新增一种交互无需改节点 switch；换背景不换场景/玩法边界，重试和客机状态正确 |
| D：统一制作与验收 | 在已稳定装配能力上完成制作窗口、内容移除预检和全链路报告 | 可从共用场景骨架建立独立验证关卡，组合已有敌人/交互/环境，不复制现有关卡专用逻辑；正式内容不因测试被覆盖 |

本地自动/Editor 验证覆盖两现有场景及独立测试组合：开局、切阶段、失败重试、暂停、回池复用、返回菜单、重新入关、池峰值、缺引用/重复 ID、重复交互/网络结果、AI 托管与交还。再用统一版本进行 PC/手机主客互换、宽屏镜头边界和真实网络验收。未出包前，模拟网络测试不能替代双端通过。

新增普通敌人不应修改章节推进代码；新增已有行为的数值变体不应新增网络消息；新机制确有新状态时才增加其适配器/契约。这里追求的是减少漏接和冲突，不承诺消灭所有 Bug，也不在本轮新增资源热更新、跨场景常驻房间或通用可视化脚本系统。
